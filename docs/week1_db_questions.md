## 4. Уже решено по вашим файлам (отвечать не нужно)

1. Образ Postgres: `pgvector/pgvector:pg16` (файл старшего). Расширение `vector` в `00001` поэтому будет работать.
2. Миграции применяются при запуске сервера (goose встроен в программу), файлы лежат в `server/migrations`.
3. Автоматическая проверка на GitHub применяет миграции на пустой базе.
4. Личные данные читаются только через `userID`, чужая запись даёт 404 (файл старшего, п. 3.1). Поэтому у каждой личной таблицы есть `user_id` или связь с ним: `profiles.user_id`, `portfolio_items.user_id`, `applications.user_id`, письма через `applications`.
5. Векторы нормированы, расстояние косинусное (файл ML). В базе индекс будет `vector_cosine_ops`.
6. Сервис моделей возвращает `model` и `dim`, сервер хранит их вместе с вектором. В базе рядом с каждым вектором будет колонка `embedding_model`.
7. `/resume/parse` возвращает `text`, `skills` (строками) и `projects` (`title`, `summary`). Проекты попадают в `portfolio_items` с `source = resume`.
8. Приведение данных и поиск дублей вакансий делает архитектор (задача А-5), не ML.
9. Задача сбора: `{"kind": "collect", "payload": {"source": ..., "date_from": ...}}`. Параметры дробления запросов лежат в `jobs.payload` (jsonb), отдельных колонок не нужно. HeadHunter отдаёт не больше 2000 вакансий на запрос, поэтому сборщик дробит запросы сам.

## 5. Решения архитектора (журнал; если с чем-то не согласны, напишите)

| № | Решение | Что это значит для вас |
|---|---|---|
| 1 | Повторный сбор вакансии **обновляет** запись в `vacancy_raw` (уникальна пара «источник + номер вакансии у источника») | Повторный запуск сбора не плодит дубли. Минус: старая версия ответа теряется (для учебного проекта допустимо) |
| 2 | Пока заведён только источник `headhunter` | Остальные источники добавим отдельным файлом (задача Т-4) |
| 3 | `sources.code = headhunter`, как в API | В коде и задачах используйте именно `headhunter`, не `hh` |
| 4 | `collection_runs` приведён к полям API: `created`, `updated`, `errors`, `error_message`, статус `partial` | Адрес `/admin/collection-runs` читает таблицу почти без преобразований |
| 5 | В очереди задач есть вид `parse_resume` | Разбор резюме идёт через очередь, статус виден в `profile.resume_status` |
| 6 | `applications`: уникальна пара (`user_id`, `vacancy_id`) | Без этого невозможен ответ 409 `application_exists` |
| 7 | Новый файл резюме заменяет старый (`resume_files`, одна строка на пользователя) | Старые файлы не накапливаются |
| 8 | Вектор по умолчанию `vector(768)`, рядом хранится `embedding_model` | Модель можно сменить, по этому полю видно, какие векторы пересчитать |
| 9 | Расширение `vector` включено в `00001` | Достаточно образа с pgvector |
| 10 | Зарплата в базе `NULL`, если не указана. Нераспознанная зарплата тоже `NULL`, не угадывается | Клиентская часть показывает «не указана», а не «0 ₽» |
| 11 | Дубли вакансий: колонка `vacancies.canonical_id` (`NULL` у основной копии, у дубля ссылка на основную) | Из неё считаются `also_on` в API и `duplicates_share` в админке |

## 7. Замечания к `openapi.yaml` (результат сверки с базой)

1. Совпадают с базой: `User`, `Me`, `Profile` (все поля и `nullable`).
2. Считаются на лету, в базе не хранятся: `score`, `explanation`, `DataQuality`, `last_success_at`.
3. Все `nullable`-поля `Vacancy` и `Profile` помечены верно (зарплата `null`, не `0`).
4. Админские адреса отдают 403, остальные чужие данные 404: согласуется с правилом из описания.
5. Названия источников в API (`headhunter`, `superjob`) совпадают с `sources.code` в базе.
