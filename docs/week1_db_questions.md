## 2. Уже решено по вашим файлам (для справки, отвечать не нужно)

1. Образ Postgres: pgvector/pgvector:pg16 (файл старшего, п. 2). Расширение vector в 00001 поэтому работает.
2. Миграции применяются при запуске сервера, goose встроен в программу. Файлы лежат в server/migrations.
3. Автоматическая проверка на GitHub применяет миграции на пустой базе.
4. Личные данные читаются только через userID, 404 для чужих записей (файл старшего, п. 3.1). Поэтому у личных таблиц есть user_id или связь с ним: profiles.user_id, portfolio_items.user_id, applications.user_id, letters через applications.
5. Векторы нормированы, расстояние косинусное (файл ML). В базе индекс vector_cosine_ops.
6. Сервис моделей возвращает model и dim, сервер хранит их вместе с вектором. В базе будет колонка embedding_model рядом с каждым embedding.
7. /resume/parse возвращает text, skills (названия строками) и projects (title, summary). Проекты идут в portfolio_items с source = resume.
8. Дубли вакансий и приведение данных делает архитектор (задача А-5), не ML.

## 5. Решения архитектора (журнал, поправьте, если не так)

1. Повторный сбор вакансии обновляет запись в vacancy_raw (UNIQUE source_id + external_id). Старая версия теряется: для учебного проекта допустимо.
2. Пока заведён только источник headhunter. Остальные добавим отдельным файлом.
3. sources.code = headhunter (как в API).
4. collection_runs приведён к полям API: created, updated, errors, error_message, статус partial.
5. В очереди задач kind = parse_resume.
6. applications: UNIQUE (user_id, vacancy_id), иначе не будет 409 application_exists.
7. Новый файл резюме заменяет старый (resume_files, PK user_id).
8. Вектор по умолчанию vector(768), решение по модели в четверг 08.10. До 18.10 поменять ещё можно.
9. Расширение vector включено в 00001.
10. Зарплата в базе NULL, если не указана (никогда не 0).
11. Дубли вакансий: колонка vacancies.canonical_id (NULL = основная копия), считает модуль приведения (А-5).
12. В profiles.work_formats добавляю CHECK (office, remote, hybrid) через ALTER в 00003: вторая линия защиты после проверки в коде.
13. Правило доступа к личным данным: функции store принимают userID первым параметром (решение старшего), у каждой личной таблицы есть user_id или связь с ним.
14. Рядом с каждым вектором храню embedding_model.
15. Письма: letters.application_id UNIQUE, letter_id в Application отдаётся через join (без циклической связи).
