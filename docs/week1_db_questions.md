## 1. Что готово

Ветка `DataBase`, папка `server/migrations/`:
- `00001_init.sql`: `users`, `profiles`, расширение `vector`.
- `00002_jobs_and_sources.sql`: `jobs` (очередь задач), `sources`, `collection_runs`, `vacancy_raw`.
- `docs/db-schema.*`: схема всей базы (черновик).

Дальше: файлы с навыками, вакансиями, портфолио, письмами, откликами. Начну после ответов ниже и выбора модели для векторов.

Что полезно знать про готовые таблицы:
- Почта уникальна без учёта регистра: перед записью и поиском приводите её к нижнему регистру.
- Регистрация создаёт пользователя и пустую строку в `profiles` в одной транзакции (хватит вставить `user_id`).
- `salary_from` может быть `NULL` («не указана»), никогда не 0.
- Допустимые значения проверяет база. Код должен проверять сам и отвечать понятным сообщением.

## 3. Решения архитектора

| № | Решение |
|---|---|
| 1 | Повторный сбор вакансии обновляет запись в `vacancy_raw` (уникальна пара «источник + номер у источника»). Старая версия теряется |
| 2 | Один источник: `headhunter`. Остальные добавим отдельным файлом (задача Т-4) |
| 3 | `collection_runs`: поля как в API (`created`, `updated`, `errors`, `error_message`). Одна строка = один запуск задачи. Статус `partial`: есть ошибки, но часть вакансий сохранена |
| 4 | Виды задач в очереди: `collect`, `normalize`, `embed`, `parse_resume`. Параметры в `jobs.payload` |
| 5 | Зарплата `NULL`, если не указана или не распознана. Никогда не 0 и не угадывается |
| 6 | Дубли вакансий не удаляются, а получают ссылку на основную копию (`canonical_id`). Поиск дублей делает приведение данных (А-5) |
| 7 | Векторы в отдельных таблицах `vacancy_vectors` и `portfolio_vectors`, рядом хранится модель. Вектор профиля не хранится: берётся среднее по векторам проектов |
| 8 | Навыки: `skills` и `skill_aliases` (варианты написания, уникальны без учёта регистра). Навыки из резюме сопоставляет сервер |
| 9 | Компании в отдельной таблице `companies`, у вакансии `company_id` |
| 10 | Письма: `letters` хранит последнюю версию, `letter_versions` историю: текст, задание для модели (`prompt_version`), доля изменённого текста (`edit_ratio`), непроверенные фрагменты |
| 11 | Файл резюме на диске, в базе путь к нему. Новый файл заменяет старый |
| 12 | `applications`: уникальна пара (`user_id`, `vacancy_id`), статусы проверяются в базе |
| 13 | Личные данные только через `userID`: у каждой личной таблицы есть `user_id` или связь с ним |
| 14 | Первый администратор назначается вручную SQL-запросом. Регистрация создаёт `is_admin = false` |

## 4. Сверка `openapi.yaml` с базой

Поля `User`, `Me`, `Profile` совпадают с таблицами. Считаются на лету и в базе не хранятся: `score`, `explanation`, `DataQuality`. Все `nullable`-поля `Vacancy` и `Profile` помечены верно. Названия источников в API совпадают с `sources.code`.
